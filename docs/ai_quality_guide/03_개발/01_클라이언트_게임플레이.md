# 개발 / 클라이언트 게임플레이

> 범위: 전투·이동·스폰·라운드·상태이상 등 게임 규칙을 실행하는 런타임 코드. UI 표시 코드는 [02_UI구현](02_UI구현.md), 성능은 [04_최적화](04_최적화.md)에서 다룬다.
> 함께 볼 파일: [01_기획/03_전투](../01_기획/03_전투.md), [01_기획/08_데이터테이블](../01_기획/08_데이터테이블.md), [06_QA/01_기능_회귀](../06_QA/01_기능_회귀.md)

## 1. 이 파트에서 AI 티가 나는 이유
AI는 "확장 가능한 구조"를 기본값으로 삼는다. 요구사항이 한 줄이어도 인터페이스, 매니저, 이벤트 버스, 팩토리를 같이 만들고, 수치는 코드에 박고, 실패할 리 없는 곳에 null 검사를 겹겹이 넣는다. 돌아가기는 하지만 읽기 어렵고, 기획 수치가 바뀌면 코드를 고쳐야 하는 코드가 된다. 그리고 실행해보지 않고 "완료"라고 보고한다. `[실무]`

## 2. AI 티 패턴
| 패턴 | 왜 티가 나나 | 대신 이렇게 | 출처 |
|---|---|---|---|
| 구현이 하나뿐인 인터페이스·추상 클래스 | 미래를 위한 구조, 지금은 간접 호출만 늘어남 | 구현이 두 개 생길 때 추출 | `[실무]` |
| `XXXManager` 싱글톤 남발 | 의존성이 숨고 테스트가 막힘 | 씬 참조 주입, 꼭 필요한 전역만 1~2개 | `[실무]` |
| 매직넘버(`speed = 3.5f`, `if (wave > 10)`) | 기획 수치가 코드에 묻힘 | ScriptableObject·데이터테이블로 분리 | `[실무]` |
| 장식 주석(`// 플레이어를 이동시킨다`) | 코드를 그대로 읽어주는 주석 | 이유가 필요한 곳에만 "왜"를 적기 | `[실무]` |
| 모든 줄에 null 검사·try-catch | 오류가 조용히 삼켜져 버그를 숨김 | 초기화 시점에 한 번 검증, 실패는 크게 실패 | `[실무]` |
| 쓰이지 않는 이벤트·옵션·파라미터 | "나중에 쓸 수도" 코드 | 요청 범위만 구현 | `[실무]` |
| `Update`에서 매 프레임 `Find`/`GetComponent` | 흔한 튜토리얼 패턴 복사 | 캐싱, 이벤트 기반 | `[실무]` |
| 테스트·실행 없이 "구현 완료" | 컴파일만 확인한 상태 | 실행 확인 + 근거(로그·스크린샷) 첨부 | `[실무]` |
| 요청 안 한 리팩터링 동반 | 변경 범위가 커져 검토 불가 | 요청 범위와 리팩터링은 별도 작업 | `[실무]` |

## 3. 작업 전에 정할 것 (프로젝트 설정값)
- 엔진·버전, 스크립팅 백엔드(Mono/IL2CPP)
- 폴더·어셈블리 정의(asmdef) 구조, 네임스페이스 규칙
- 수치 데이터 위치(ScriptableObject / CSV / JSON)
- 코드 스타일(포매터 설정 파일, 네이밍 규칙)
- 테스트 방식(EditMode/PlayMode, 헤드리스 시뮬레이션 여부)
- 보호 대상(바꾸면 안 되는 밸런스·연출 값)

값은 [프로젝트 설정](../00_공통/03_프로젝트설정_템플릿.md)의 "개발"에 적는다.

## 4. 작업 규칙
1. **요구사항을 한 문장으로 다시 쓴다.** 입력·출력·완료 조건이 안 나오면 구현하지 않고 묻는다.
2. **기존 코드를 먼저 읽는다.** 같은 일을 하는 클래스가 있으면 새로 만들지 않고 확장한다.
3. **수치는 데이터로 뺀다.** 기획자가 바꿀 수 있는 값은 코드에 두지 않는다. 상수로 남는 값은 이름을 붙인다.
4. **가장 단순한 구조로 만든다.** 클래스 수, 파일 수가 요청 대비 과하면 다시 줄인다.
5. **실패는 초기화에서 잡는다.** `OnValidate`, `Awake`에서 참조 누락을 검사하고 런타임 경로에는 검사를 두지 않는다.
6. **테스트로 증명한다.** 규칙 계산(데미지, 경제, 스폰 순서)은 EditMode 테스트, 흐름은 PlayMode 스모크 테스트.
7. **변경 요약에는 근거를 붙인다.** 바뀐 파일, 실행 결과, 테스트 결과, 남은 문제.

## 5. 금지
| 금지 | 이유 | 예외 |
|---|---|---|
| 요청 없는 새 매니저·전역 상태 | 결합도 증가 | 사용자가 구조 변경을 승인 |
| 기획 수치 하드코딩 | 밸런스 수정 때 코드 변경 필요 | 물리 상수 등 바뀌지 않는 값 |
| 빈 `catch {}` / 오류 무시 | 버그 은폐 | 외부 IO에서 의도적 폴백 + 로그 |
| 보호 대상 값 임의 변경 | 승인된 게임 감각 훼손 | 명시 승인 |
| 씬·프리팹 YAML 직접 편집 | 참조 깨짐 | 없음. 에디터 API 사용 |
| 실행 확인 없는 완료 보고 | 사실과 다를 수 있음 | 없음 |

## 6. 요청서 예시
```
[목표] 화상 상태이상 추가. 3초간 초당 최대체력 2% 피해, 중첩 없음, 재적용 시 시간만 갱신.
[맥락] 기존 둔화(Slow) 상태이상과 같은 구조를 따른다. 기존 파일을 먼저 읽고 재사용해라.
[숫자 스펙] 지속·틱 간격·비율은 상태이상 데이터 에셋에 넣고 코드에 쓰지 마라.
[금지] 새 매니저 클래스, 쓰이지 않는 옵션, 장식 주석, 다른 상태이상 리팩터링.
[검증] EditMode 테스트: 틱 횟수, 재적용 갱신, 사망 시 해제. 결과 로그를 붙여라.
[산출물] 변경 파일 목록 + 테스트 결과 + 확인하지 못한 것.
```

## 7. 검증 체크리스트
- [ ] 컴파일 오류·경고 0 (새로 생긴 경고 포함)
- [ ] 관련 EditMode/PlayMode 테스트 통과, 결과 첨부
- [ ] 새 수치가 모두 데이터 에셋에 있음 (코드 검색으로 숫자 리터럴 확인)
- [ ] 새 클래스·파일 수가 요청 규모에 맞음
- [ ] 런타임 경로에 `Find`, 매 프레임 할당 없음
- [ ] 실제 플레이에서 동작 확인 (스크린샷 또는 짧은 영상)
- [ ] 사람이 손맛·타이밍을 직접 플레이해 판단
