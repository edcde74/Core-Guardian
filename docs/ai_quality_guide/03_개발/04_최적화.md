## 1. 이 파트에서 AI 티가 나는 이유
AI는 측정 없이 "흔히 느린 것"을 고친다. 문자열 연결, LINQ, `GetComponent`를 일단 바꾸고 "성능이 개선되었습니다"라고 보고한다. 실제 병목이 아닌 곳을 고쳐 코드만 복잡해지고, 화질이나 게임 감각이 같이 떨어진 것을 놓친다. `[실무]`

## 2. AI 티 패턴
| 패턴 | 왜 티가 나나 | 대신 이렇게 | 출처 |
|---|---|---|---|
| 측정 없는 최적화 | 추측으로 고침 | 프로파일러로 병목 확인 후 수정 | `[실무]` |
| "개선되었습니다"만 있고 숫자 없음 | 근거 없음 | 같은 조건 전후 ms·FPS·할당량 표 | `[실무]` |
| 에디터에서만 측정 | 빌드와 수치가 다름 | 개발 빌드·실제 빌드에서 실측 | `[실무]` |
| 평균 FPS만 보고 | 끊김(스파이크)을 숨김 | 최소·최대·평균·1% low | `[실무]` |
| 화질·연출 값을 몰래 낮춤 | 품질 회귀 | 품질 비교 스크린샷 첨부 | `[실무]` |
| 병목 아닌 곳의 미세 최적화 | 읽기 어려워지기만 함 | 상위 비용 항목부터 | `[실무]` |
| 실패·악화 결과 생략 | 보고 왜곡 | 실패도 기록 | `[실무]` |

## 3. 작업 전에 정할 것 (프로젝트 설정값)
- 목표 프레임(예: 60fps = 16.6ms)과 최저 사양 기기
- 측정 장면과 재현 조건(라운드, 적 수, 카메라 위치, 시간)
- 측정 도구(엔진 프로파일러, 빌드 내 성능 표시, 외부 도구)
- 보호 대상(바꾸면 안 되는 화질·연출·밸런스)
- 예산: 프레임당 GC 할당, 드로우콜, 메모리 상한

## 4. 작업 규칙
1. **재현 조건을 고정한다.** 같은 장면, 같은 시점, 같은 빌드 설정으로 측정한다.
2. **기준선을 먼저 잰다.** 최소·최대·평균 FPS, 프레임 시간, GC 할당, 드로우콜.
3. **병목을 찾는다.** 프로파일러 상위 항목부터 본다. 추측으로 고르지 않는다.
4. **선택지를 먼저 보고한다.** 줄일 방법 2~3개와 예상 효과·위험을 적고 사람이 고르게 한다. `[실무]`
5. **한 번에 하나씩 바꾼다.** 여러 개를 동시에 바꾸면 무엇이 효과였는지 모른다.
6. **같은 조건으로 다시 잰다.** 절감량과 절감률을 기록한다.
7. **품질 회귀를 확인한다.** 전후 스크린샷·영상을 나란히 비교한다. A/B 비교 이미지로 만들면 판정이 쉽다. `[영상]`

## 5. 금지
| 금지 | 이유 | 예외 |
|---|---|---|
| 측정 없는 수정 | 효과 불명 | 명백한 버그(매 프레임 Find 등) |
| 보호 대상 값 하향 | 승인된 품질 훼손 | 사람이 선택지에서 고른 경우 |
| 결과 숫자 없이 완료 보고 | 근거 없음 | 없음 |
| 무거운 진단(딥 프로파일 등) 무단 실행 | 에디터 멈춤 | 승인 |
| 악화·실패 숨김 | 판단 왜곡 | 없음 |

## 6. 요청서 예시
```
[목표] 웨이브 20 이후 프레임 끊김 원인 파악.
[조건] 개발 빌드, 1920x1080, 웨이브 20 시작 후 30초, 카메라 기본 위치.
[단계] 1) 기준선 측정(최소/최대/평균 FPS, GC/프레임, 드로우콜). 2) 상위 비용 5개 표.
       3) 줄일 방법 선택지 2~3개와 예상 효과·위험. 여기서 멈추고 보고.
[금지] 이 단계에서 코드·설정 수정, 화질 하향.
```
