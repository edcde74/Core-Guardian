# 마스크 전용 텍스처 아틀라스 설계

2026-10-21. **설계만 작성한 상태이며 미구현·미적용**이다. 사용자는 동일 텍스처 묶기의 실제 절감 실패 후 텍스처 아틀라스 설계를 선택했다. 다음 구현은 이 설계를 검토한 뒤 범위를 정한다. 현재 게임의 성장·물량·원본 그림·보행·방향·그림자·강조·HUD·효과 수/수명·소리는 유지한다.

## 해결할 문제와 선택

[직전 실험](mask_batch_20261021/README.md)에서 128적/15포탑의 마스크 소유자274개가 파츠1304개를 제출했고 동일 텍스처로 묶인 소유자는0개였다. Draw Calls3208/SetPass1608은 전후 동일했다. **다른 파츠 텍스처를 같은 페이지에 복사한 뒤 마스크 메시를 페이지별로 묶는 것**이 이번 설계다.

|방식|영향과 비용|선택|
|---|---|---|
|원본 Sprite 전체를 네이티브 SpriteAtlas에 바인딩|본체에도 영향을 줄 수 있으나 동적 잘라내기 좌표·패킹 회전/트리밍 검토가 필요|후속 별도 범위|
|마스크 전용 페이지+매핑 자산을 Editor에서 생성|원본 본체 경로 유지, 마스크용 텍스처 메모리가 추가됨|이번 권장안|
|런타임 텍스처 패킹|실행 중 준비 시간·임시 메모리·반복 생성 관리가 추가됨|보류|

원본 코드 근거: [OriginalMotion](../../Assets/Scripts/CoreGuardianOriginalMotion.cs:42)은 `source.textureRect`에서 좌표를 더해 `Sprite.Create(source.texture,...)`를 호출한다. [OriginalWalk](../../Assets/Scripts/CoreGuardianOriginalWalk.cs:196)도 원본 rect/texture를 사용한다. 원본 전체에 아틀라스를 적용하면 이 가정을 다시 검증해야 한다. 별도 마스크 페이지는 이 코드와 본체 Sprite 참조를 바꾸지 않는다.

Unity의 [Sprite.Create](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Sprite.Create.html)는 지정 텍스처의 rect로 Sprite를 만든다. 네이티브 아틀라스의 [packing 설정](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/U2D.SpriteAtlasPackingSettings.html)에는 rotation/tight packing/padding이 있다. 이 설계는 자동 바인딩 설정을 변경하지 않는 별도 페이지 방식이며, 구현 때 현재6000.6.2f1의 실제 API를 다시 확인한다.

## 데이터와 생성 경로

생성 입력은 실제 마스크 경로에서 사용하는 원본 Texture2D다. 공격/방어/버프/보스/플레이어/단일·다중·지원 포탑의 방향·피격·발사 위상을 조사한다. HUD/폰트/무관한 Resources 전체를 패킹하지 않는다. 현재128적 조사만으로 모든 상태의 텍스처 목록이 완전하다고 가정하지 않는다.

**Sprite 조각 대신 원본 텍스처 전체를 한 항목으로 복사**한다. 런타임에 만든 Sprite도 원본 texture와 원본 UV로 같은 항목을 찾을 수 있다. 매핑에는 원본 Texture2D 참조, 페이지 참조, 원본 크기, 페이지 내 픽셀 원점/크기, 입력 GUID·내용 해시·생성 버전을 저장한다.

예정 경로는 `Assets/Resources/CoreGuardian/MaskAtlas/` 아래 페이지와 manifest 자산, 생성기는 `Assets/Editor/CoreGuardian/MaskAtlasBuilder.cs`다. 아직 생성하지 않았다. 기존 자산/씬/패키지·SpritePackerMode는 변경하지 않는다. 명시적으로 실행한 Editor 생성만 허용하고 자동 빌드에 연결하지 않는다.

- 함께 쓰는 한 개체의 파츠를 같은 페이지에 우선 배치한다. GUID/경로와 크기를 이용해 정렬·패킹 결과를 결정적으로 만든다.
- 최대2048픽셀을 초기 페이지 설계 상한으로 두되 실제 면적에 맞는 크기를 사용한다. 처음부터2048²를 여러 장 할당하지 않는다. 실제 지원 기기 상한과 메모리는 구현 시 확인한다.
- 회전·트리밍·축소·색/알파 보정 없이 원본의 실제 로드된 알파를 보존한다. 초기안은 RGBA32, Point, Clamp, mipmap 없음이다. 원본 importer/PNG의 Read/Write·압축 설정은 일괄 변경하지 않는다.
- 항목 간4픽셀 여백과 가장자리 복제로 원본 Clamp 샘플링을 보존한다. 실제 UV 경계에서 같은 결과인지 검사한다. 기존 마스크 RT padding과 다른 설정이다.
- 원본을 읽을 수 없으면 Editor가 소유하는 복사/읽기 경로를 사용한다. 지원하지 않는 소스·상한 초과·겹침은 오류로 보고하며 자동 축소하지 않는다. 최종 API와 복사 정밀도는 구현 전 작은 입력으로 확인한다.

## 렌더링 변경

마스크를 그릴 때 원본 Sprite의 기하·pivot·PPU·flip·파츠 행렬은 그대로 사용한다. UV만 다음처럼 매핑한다. 원점과 크기는 픽셀 단위이고 UV 방향은 실제 엔진 소스와 일치시킨다.

`atlasUV = (entryOriginPx + sourceUV * sourceTextureSizePx) / pageSizePx`

소유자 내부에서 **같은 페이지+정확히 같은 opacity**인 파츠를 한 메시로 묶는다. GPU에서 파츠별 행렬을 적용하는 직전 후보의 방법을 재사용하되 검증된 기록이 곧 새 아틀라스 경로의 통과를 뜻하지는 않는다. 다른 페이지/alpha, 인덱스 한도 초과는 분리한다. 매핑 없는 텍스처는 기존 개별 그리기로 출력하고 누락 건수를 진단한다. 누락을 숨기거나 그림을 생략하지 않는다.

이번 단계에서 RT 개수, 강조/그림자 소비자 수, 효과 모양과 합성 셰이더는 줄이지 않는다. 동일 본체의 마스크 결과를 공유하는 최적화는 별도 단계다. 본체 렌더링의 호출 감소도 이번 목표에 포함하지 않는다.

## 수명과 비용

manifest·페이지는 Unity가 관리하는 불변 자산으로 취급하며 개체 제거 때 Destroy하지 않는다. 개체별 결합 메시·캐시는 기존 소유자의 종료 경로에서 해제하고, 원본 Sprite/계층 또는 manifest 버전 변경 때 재구성한다. 매 프레임 페이지를 만들거나 패킹하지 않는다.

원본 텍스처가 본체에 계속 필요하므로 **메모리 절감안이 아니다**. RGBA32 페이지의 기초 용량은 `width × height × 4`이며2048² 한 장은16MiB다. 실제 엔진 메모리에는 복사본·메타데이터·업로드 임시 메모리·메시 버퍼가 더해질 수 있다. 페이지 수/공간 사용률, 생성·로딩 시간, 준비 시 최대/안정 상태 텍스처 및 메시 메모리, 반복 초기화 후 잔존량을 보고한다. 허용 예산은 미확정이다.

## 성공 기준과 검증 순서

1. 공격형의 실제 서로 다른5개 파츠부터 같은 페이지에 넣어 실제 마스크 제출5→1이 가능한지 확인한다. 합성용 가짜 입력만 통과한 결과로 적용하지 않는다. alpha·페이지 분리와 미등록 원본 fallback도 확인한다.
2. 모든 등록 원본 알파와 페이지 복사값을 픽셀 단위로 대조한다. 페이지 가장자리/회전/flip/중첩/부모 스케일과 동적 잘라낸 Sprite를 포함한다.
3. 기존8역할×432 조건의 효과 출력3456건과 비어 있지 않은 출력 건수를 보고한다. 본체 포함 실제 프레임 비교도 수행하고 보스 전체 합성의 기존 미확정9건은 원본 대조군과 구분한다. 아틀라스 변경으로 생긴 차이는0이어야 한다.
4. 사용 중 Play/다른 검사가 없는 때에만 동일128적/15포탑, 해상도·줌·배속·VSync·Profiler 항목을 맞춰100프레임×3회 비교한다. Draw Calls·SetPass·CPU·프레임 간격·GC·메모리·FPS 최소/최대/평균과 절감량/율, 실제 페이지별 그룹 수·fallback 수를 원본과 함께 남긴다. 기존 전 측정이 조건상 낡아졌으면 재측정한다.
5. 승인된 자체 반복 초기화600프레임×3회의 RT·메시·페이지 잔존과 원복을 확인한다. 장시간/정상30R/standalone 판정은 별도이며 자동 빌드·실행파일 실행·push는 하지 않는다.

1304개 마스크 그리기가 각 소유자에서 한 페이지·한 alpha로 묶인다면274개가 조건부 목표다. 여러 페이지/alpha면 더 많아진다. 이는 Frame Debugger 이벤트 수준의 목표이며 Stats3208/1608에서 그대로 빼거나 FPS로 환산할 수 없다. SetPass 감소 여부도 실제 측정한다. RT clear274개는 이번 범위에 남는다.

픽셀 차이, 원본 표시 손상, 호출 절감 없음, 변동 범위를 넘어선 CPU/프레임 악화·메모리 증가가 발견되면 그대로 적용하지 않고 원인과 비용을 보고한다. 텍스처 추가 비용과 실제 호출 이득을 확인한 뒤 유지 여부를 판단한다.
