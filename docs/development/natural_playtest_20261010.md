# 1~9라운드 자동 조작 연속 실행 — 2026-10-10

## 목적과 방법

기존 전체 라운드 검사는 적을 강제 처치했다. 이번에는 실제 전투 씬의 Play Mode에서 정상 이동·설치·강화·전투 시작 API와 기존 Update/자동 공격만 사용했다. 체력·재화·공격 수치·CSV를 주입하거나 변경하지 않았다.

- 대상: `Assets/Scenes/CoreGuardian_CombatPrototype_20261008.unity`, Unity 6000.6.2f1.
- 실행기: [MeasureNaturalRounds.cs](MeasureNaturalRounds.cs). Assets 밖의 임시 컴파일 스크립트로 실행하므로 게임에 관찰용 컴포넌트를 추가하지 않는다.
- 시간: `Time.timeScale=5`. 준비는 정상 전투 시작 명령으로 넘겼다. 표의 시간은 배속을 적용한 게임 시간이며, 에디터 관찰 프레임의 오차를 포함한다.
- 기술병: 초기 (15,10)에서 `TryStep`으로 한 칸씩 위로 이동한 뒤 고정. 설치·강화도 정상 구매 API를 사용했다. 마우스 클릭·키보드 입력·기술병의 지속적인 이동을 재현한 사람 플레이테스트는 아니다.
- 기술병 강화: 준비 시 잔액이 충분하면 공격력 강화 구매. 구매 가격은 실제 계산 결과 사용. 지원 포탑은 이번 세 실행에서 구매 조건에 도달하지 않았다.
- 각 실행은 새 Play 세션으로 시작했다. 종료 시 배속은 1로 복구됐고, 최종 Play를 종료했다.

첫 두 선택은 같은 위치를 사용했다. 5R 코어 피해는 저장 선택 10, 포탑 강화 선택 6이었다. 강화 선택이 누수를 줄였지만 이 배치에서는 9R까지 방어하지 못했다. 패배 라운드는 완료 보상이 0이었다.

근접 배치는 포탑과 기술병을 모두 한 칸 이동했다. 따라서 성공 원인을 포탑 이동 하나로 분리하거나 최적 배치로 결론내릴 수 없다. 기술병 실제 피해가 3R부터 발생했으며, 범위 포탑은 8~9R에서만 피해에 기여했다. 범위 포탑·지원 포탑이 반드시 필요한 난이도라는 근거도 아니다.

## 관찰과 다음 확인

- 위치에 따른 공격 기여 차이가 크다. 저장 선택의 범위 포탑 (17,15)은 상단 경로 y=18과 거리 3으로 기본 사거리 한계에 걸린다. 이번 실행에서 실제 피해 기여가 0이었다. 화면상 가까워 보여도 경로를 충분히 덮지 못하는 배치를 사용자가 구분할 수 있는지 확인할 필요가 있다.
- 3R부터 누수하면 전투 종료까지 시간이 약 107~114초로 늘었지만, 근접 배치에서는 3~9R 약 44~47초였다. 사람 플레이에서 적이 남은 이유와 현재 공격 범위를 읽을 수 있는지 확인한다.
- 저장된 실제 화면에서 왼쪽 포탑 정보 패널이 적 진입 경로 일부를 가린다. 가림이 조작·판독을 방해하는지는 실제 입력 플레이로 확인한다. 이번에는 승인된 HUD/아트/크기를 변경하지 않았다.
- 설치 커서·Esc·피해 숫자·명중 체감·버프/체력 막대 겹침은 이번 자동 조작만으로 승인하거나 완료 처리하지 않는다.
- 다음 우선 작업은 1배속 실제 입력 플레이, 배치/사거리 판독, 다른 위치·강화 선택의 반복 비교다. 수치 조정은 그 결과를 근거로 결정한다. 10R 보스·증강·11R·최신 Windows 빌드는 여전히 미구현이다.

## 검증·도구 제한

관찰 스크립트 최종 dry run 컴파일 성공, diagnostics 없음. 종료 후 `BuildCombatPrototype.Verify`의 내부 success=true, 승인 A 길·적/포탑 3종·참조·저장 상태·초기 위치 (15,10)를 확인했다. 에디터 ready, compiling=false, domainReloadInProgress=false, Play stopped, timeScale=1.

게임 코드와 실행 CSV를 변경하지 않았으므로 기존 EditMode 28/PlayMode 6 테스트는 이번에 다시 실행하지 않았다. 그 수치는 이전 회귀 결과다. 이번 신규 증거는 세 실행의 라운드 기록과 종료 후 씬 검사다.

첫 실행 중 `capture_game_view`에 금지된 `..` 경로를 전달한 도구 명령 오류 1건이 로그에 기록됐다. 게임 전투 예외와 구분한다. 두 번째·세 번째 실행의 runtimeErrors는 비어 있다. 첫 실행에서 Unity JsonUtility가 임시 어셈블리의 rounds 목록을 파일에 누락해, 종료 후 메모리의 전체 기록을 Newtonsoft로 복구했다. 실행기의 저장 함수도 Newtonsoft로 수정했고 이후 두 실행에서 전체 라운드 배열 저장을 확인했다.
