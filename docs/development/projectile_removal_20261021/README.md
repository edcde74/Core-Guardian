# 탄환 제거 묶음 처리

2026-10-21 Asia/Seoul. 복구 기준 `e0ffc77`. 사용자는 탄환 처리 순서·피해·속도·표시 수를 유지하는 제거 최적화를 승인했다. Play·자동 테스트·성능 측정 보류 지시는 계속 적용한다.

## 근거와 구현

이전 Session은 틱의 탄환 스냅샷을 순회하면서 퇴장/명중마다 `Projectiles.Remove(p)`로 처음 일치 항목을 검색하고 뒤쪽을 이동했다. 제거 R회·현재 목록 N개일 때 반복 검색/이동 비용이 생기는 구조다. 실제 병목 비중은 계측하지 않았다.

계획과 구현은 다음 범위다. 이동·명중은 원래 스냅샷 순서로 처리하고, 이벤트 없는 구간의 제거를 호출별 StepWork 사전에 참조별 횟수로 기록한다. 정리 시 목록을 한 번 순회하며 처음 해당 횟수만큼 제거하고 생존 순서를 보존한 뒤 `RemoveRange`로 꼬리를 정리한다. 중복 객체 참조도 기존 반복 `Remove`와 같은 횟수만 없앤다. 사전은 작업 버퍼와 함께 재사용하며 finally에서 참조를 비운다.

`DamageApplied` 구독자가 있는 명중은 앞선 제거를 먼저 반영하고 `ApplyDamage`를 호출한 뒤 현재 탄환을 기존 `Remove`로 제거한다. 관찰자는 이전과 같이 현재 탄환은 포함하고 앞서 없어진 탄환은 제외한 목록을 본다. 관찰자가 목록을 비우거나 재정렬/추가하거나 Tick에 재진입할 수 있어 이 경로는 묶지 않는다. 독립 호출 버퍼를 유지하고 예외 시에도 앞선 제거만 finally에서 반영한다. NaN 거리에서 명중하지 않는 원래 `Distance <= .00001f` 조건도 유지했다.

변경 범위는 Session 제품 소스1개·기존 EditMode 검사 소스1개다. 모델 풀링·피해/발사 순서·탄환 이동식/속도·사거리·타깃 규칙·CSV·표시·효과·사운드는 변경하지 않았다.

## 제한과 검증

- 콜백 없는 구간은 정리1회가 목록 N·제거 R에 비례하는 구조다. 정상 게임의 피해 구독자가 있는 명중은 기존 제거를 유지하므로 이득이 제한된다. 이벤트 직전 정리·사전 조회 비용 때문에 조건에 따라 악화될 수도 있다.
- 사전은 제거 종류 수만큼 용량이 늘며 Clear 후 용량을 유지한다. 기존 StepWork 풀 최대8개에 각각 속한다. GC/잔류·피크 메모리와 CPU의 실제 득실은 미측정이다.
- 독립 읽기 전용 코드 리뷰에서 수정 필요 사항 없음. `git diff --check` 통과. 공식 Unity MCP 재컴파일 completed/failed=false/errors=[]/compilationFailed=false. 현재 Console 오류0·경고118, 새 경고115개는 UAC0005 36·CS0618 79이며 변경 제품 소스 경고0이다.
- 회귀 검사 소스6개 추가: 생존 순서/중복 제거, 관찰 목록/목록 교체와 스냅샷 후속 명중, Tick 재진입, 관찰자 예외, 후속 처리 예외에서 앞선 제거 보존, 비유한 좌표 비명중. **컴파일만 했으며6개 모두 미실행**이다. 기존 검사를 반복하지 않았다.
- 전투씬1/dirty=true(수정 전부터 사용자 상태), Play stopped/컴파일·domainReload=false, 실행 중 테스트 없음. 씬 저장/복원 없음. 사용자 설정3파일 해시가 기존 기록과 일치했고 설정2파일 변경·미추적·폰트 도구 접근오류 표시는 보존했다. 빌드·실행파일 실행·push 없음.
- [컴파일/전후 에디터 상태/경고 요약](verification.json), [컴파일한 소스 해시](implementation_hashes.json).
