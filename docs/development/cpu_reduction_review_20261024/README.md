# CPU 절감 방향과 실패 후보 재평가

2026-10-24 Asia/Seoul. 사용자 요청에 따라 모든 분야를 검토하고, 큰 비용부터 처리할 순서와 실패 방법의 재적용 조건을 정리했다. 이번 작업은 기존 자료 분석·소스 확인·보고서 작성만 수행했다. 새 Unity 연결/Play/Profiler/재로딩/테스트·제품/씬/설정 변경·빌드/실행파일/커밋/push는 하지 않았다. 아래 내용은 실행 제안이며 승인된 구현 계획은 아니다.

## 1. 판단과 진행 방향

**첫 대상은 마스크를 중심으로 한 표시 준비·출력과 렌더 제출 구조다.** 작은 좌표·문자열 중복을 계속 고치는 방식으로 큰 CPU 절감 목표를 해결하지 않는다. 동시에 뷰·애니메이션·전투·HUD·GC·오디오·효과·리소스·엔진 설정도 검토 목록에 포함한다.

접근법은 세 가지다. 작은 C# 수정만 계속하면 위험은 작지만 지난 좌표 후보처럼 효과도 작을 수 있다. 렌더 구조를 한꺼번에 교체하면 대상은 크지만 정렬·픽셀·수명 실패가 섞인다. 따라서 **큰 비용별로 구조 개선을 분리하고, 한 단계가 끝날 때 다음 최대 비용을 다시 고르는 방식**을 권고한다.

마스크 입력 재사용 A는 효과가 없다고 확인된 후보가 아니다. 검사 오류로 성능 평가까지 못 갔으므로 유한한 검증으로 결론을 낼 가치가 있다. 다만 A만 반복하지 않고, 효과가 작으면 출력·색상 왕복·제출 구조로 넘어간다. 미측정 영역을 작은 비용이라고 가정하지 않는다.

## 3. 가장 먼저 줄일 표시·렌더 CPU

### 마스크4.88ms: 기존 A 후보의 실제 효과 판정

기존 후보는 구현·대상47테스트 이력과 수정한 격리 두 사례 통과가 있다. 제품은 현재 원본이다. 수정 도구의 활성 Renderer 강제 검사와 원본 자기 비교를 유지해 기존512조합의 동등성 범위를 마무리하고, 같은 일반 성능 조건으로 후보3회를 비교하는 것이 후속안이다. 유효한 원본3회는 소스·환경·계측 조건을 확인해 재사용한다.

줄이는 것은 같은 Present 안의 sprite/color/flip/matrix/bounds/sort 반복 native 읽기다. 투영·실제 움직임·생산 전체가 없어지는 후보가 아니므로 4.88ms 전체가 절감 가능량은 아니다. 해당 계획의 목표1ms·0.5ms 미만이면 큰 비용 목표 미달이라는 판정선을 유지한다. 변동 겹침·품질/전체 프레임 회귀도 구분한다. 이득이 작으면 같은 미세 후보를 확대·반복하지 않는다.

owner별 입력 버퍼와 full sample 목록은 메모리 증가 가능성이 있다. 용량·잔류를 측정해 기존 계획의 메모리 회귀 거부 조건과 대조한다. CPU 개선만으로 추가 메모리 절충까지 자동 승인하지 않는다.

### 마스크 생산·출력·복사 구조의 추가 개선

현재는 개체별 bounds/crop·cache 검사·출력 설정과, 페이지 생산 뒤 개별 RT로 CopyTexture하는 구조다. 다음 두 갈래를 분리한다.

- **준비·출력의 반복 native 호출과 업로드 줄이기:** 카메라/viewport 입력, source 구조 확인, quad·정렬·PropertyBlock에서 중복을 찾는다. 콜백 뒤 바뀔 수 있는 값은 live로 읽는다. QuadUpload 약0.30ms만 고쳐 큰 목표라고 보고하지 않는다. 페이지 mesh도 매 Flush마다 Clear/SetVertices/SetUVs/SetTriangles/SetData를 수행하므로 불변 topology와 변동 데이터를 분리할 수 있는지 검토한다. PageProducer 전체 약0.5ms도 그 작업의 상한이다.
- **출력에서 페이지 직접 참조:** 내부 emphasis 소비자부터 page/region을 직접 읽으면 copyback·개별 RT 바인딩/전환을 줄일 여지가 있다. 기존 Renderer·정렬을 남기고 거대한 출력 mesh 병합부터 하지 않는다. 다만 원래 작은 Texture의 Clamp·여백·Point raster, generation/pending·다중 카메라·외부 소비자 계약을 보존해야 한다. 복사 비용 단독 ms는 미측정이므로 제거 시 몇 ms라고 약속하지 않는다. 기존 개별 RT API/fallback을 유지하는 opt-in 설계를 먼저 검토한다.

출력 MeshRenderer의 MPB·셰이더 상수·재질/텍스처 전환도 검토한다. Unity는 일반 SRP Batcher 호환 조건에 MPB 미사용과 UnityPerMaterial 상수를 명시한다. 이를 SpriteRenderer의 2D native 배칭에 그대로 대입하거나 전역 SRP OFF로 해결하지 않는다. [Unity 호환 조건](https://docs.unity3d.com/6000.0/Documentation/Manual/SRPBatcher-Materials.html). 고급 mesh 버퍼 API는 선택 수단이며 레이아웃·bounds·인덱스 검증을 보존해야 한다. [SetVertexBufferData](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Mesh.SetVertexBufferData.html).

### 본체 색상 적용1.03~1.10ms와 종료 복원 줄이기

현재 카메라 시작에 본체별 color를 읽고 쓰며 종료에 다시 읽어 복원한다. 새 방향은 **같은 밝기1.15를 표시 셰이더/공용 재질 경로로 표현해 왕복 setter를 줄이는 것**이다. 밝기·강조 효과를 낮추는 제안이 아니다.

색공간 변환 앞뒤의 곱셈 위치가 다르면 결과가 다르다. native 색 양자화/HDR·alpha·피격/외부 tint·MPB·재질 교체·다중 카메라·비활성 복원·원본 Sprite identity와 정렬을 지켜야 한다. 일반/HDR/피격 픽셀을 작게 입증하고 미지원 재질은 원본 경로로 남기는 방향이다. 약1ms 전체가 제거된다고 확정하지 않는다.

### 본체 배칭의3.81ms 준비 비용을 고쳐 Draw 감소를 실익으로 연결

과거 native 후보는 약559 Draw를 줄였다. 실제 배칭 가능성은 있지만 후보 자체 CPU3.812ms가 생겨 그대로 활성화할 대상은 아니다.

1. 초기화 실패 시 부분 리소스 정리, 카메라 사이 재질 변경·owner 비활성 시 복원을 먼저 보완한다.
2. shader/texture/layer 등 정적 메타데이터를 등록 시 정리하고 shader.name 반복 문자열을 없앤다. alpha·외부 MPB·활성·재질 변경을 무조건 캐시하지 않는다.
3. 560부품의 카메라별 SetPropertyBlock·color·material 교체/복원이 중요한 조사 대상이다. 메타데이터 조회만 줄여3.81ms가 사라진다고 가정하지 않는다. native 쓰기가 지배하면 표시 입력 전달 구조를 바꿔 왕복을 줄여야 한다. 원본 identity/정렬을 깨뜨렸던 신규 Sprite·수동 병합 mesh를 그대로 반복하지 않는다.
4. 안전성·CPU·GC·전체 프레임 이득을 확인해야 활성화를 판단한다. 이득이 없으면 OFF를 유지한다.

2D 정렬에는 layer/order 외에도 render queue·거리·재질/셰이더·동률 처리가 관여한다. [Unity6.6 정렬 문서](https://docs.unity.com/en-us/engine/6000.6/manual/unity2d/sprite/sort-sprites/sort-sprites). 순서를 추측한 병합으로 다시 접근하지 않는다.

## 6. 실행 단위와 판단 기준

1. **큰 비용 귀속 보충:** 기존 자료를 재사용하고 Main/Render/대기·복원 비용 등 부족한 부분만 짧은 일반 캡처로 보충한다. 예시는128/15,warm15/sample90 한 회,Deep OFF,고정 마커와 상위 Main/Render 구간 제한 추출이다. 실제 시간·표본 상한·화면 고정·종료/복원은 실행 승인 때 고정한다. 새120초·전체 Deep 추출은 제안하지 않는다.
2. **마스크 A 판정:** 동등성 범위 마무리→동일 조건 후보3회→CPU/전체 frame/GC/메모리로 채택·복구 결정. 원본 전체를 관성적으로 재측정하지 않는다. 픽셀 실패 시 경계 자료를 보존하고 후속 반복 중단.
3. **다음 최대 구간:** 실제 귀속에 따라 마스크 출력/반복 준비, 틴트 왕복, native 제출 중 하나를 설계·구현·측정한다. 현재 이 셋을 큰 개선 후보로 본다. 절감 ms는 미측정이며 합산 효과를 보장하지 않는다.
4. **뷰·전투·UI/GC·기타 재정렬:** 수정 뒤 최대 비용이 옮겨가면 그 분야를 다음으로 올린다. 모든 분야를 처리 목록에 두되 효과가 작은 후보의 비싼 반복 검사는 피한다.
5. **정상 부하·기기 검증:**128/15 주입 비교와 정상 초반/중후반·실제 최대 부하를 구분한다. 장시간·목표 기기·Player 검증은 별도 범위를 정한다. 빌드/실행파일은 현재 승인 범위가 아니다.
