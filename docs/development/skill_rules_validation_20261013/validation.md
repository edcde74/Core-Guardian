# 두 분석 스킬 공통 규칙 보완·예시 실행 검증

2026-10-13. 게임 구현 변경 없음. 프로젝트 원본 스킬 2개를 보완하고 개인 설치본에 동기화한다.

## 7개 요구 확인

1. 두 진입 문서에 적용 AGENTS.md·현재 사용자 지시 준수와 기존 작업 시작/종료·Git·인수인계 규칙을 재정의하지 않는다고 명시했다. 분석은 게임 읽기 전용, 종료 시 담당 분석 링크/실제 확인 범위만 인수인계 갱신한다.
2. 코어가디언 전용 범위를 명시했다. 밸런스는 난이도/성장 수지, HUD는 표시/조작/성장 전달 담당이다. 상대 스킬과 담당 노션으로 연결하고 기존 기능/계측을 중복 구현하지 않는다.
3. `core-guardian-balance`의 설명은 초반 지루함·빌드/DPS/클리어 분석, `core-guardian-hud-ux`의 설명은 강화 표시·증강 UX·접기·통합 지표 판단의 사용 조건을 이미 구체적으로 제시하므로 유지했다. UI 기능 구현 요청의 권한을 분석 스킬에서 확대하지 않는다.
4. 기존 Notion fetch, Unity 상태 조회, 기존 CSV 분석 스크립트와 과거 계측/테스트 기록을 재사용했다. 새 게임 테스트/Play는 실행하지 않았다. 이번 실제 editor_status는 CD ready/stopped/compiling=false, domainReload=false였다.
5. 아래 예시 2개를 스킬 절차로 수행했다. 이전 독립 forward-test 기록도 연결한다. 형식 검사만으로 실제 행동 검증을 대체하지 않는다.
6. 기존 5단계 분석 절차/6항목 보고, HUD 4단계 조사/7항목 보고를 유지했다. 긴 도구 매뉴얼/새 기능/테스트 체계를 추가하지 않고 공통 의사결정 문구만 보완했다.
7. 두 스킬에 확인 데이터/추정/주관적 평가 표시와 평가 조건/미검증 여부를 명시했다. 기획·구현·계측을 확인 데이터 안에서도 구분한다.

## 예시 1 — 밸런스

요청: `$core-guardian-balance 현재 1~3라운드에서 첫 플레이어 강화 가능 시점과 공격력 1회 강화의 효과를 읽기 전용으로 분석해 줘.`

기존 `scripts/analyze_rounds.py`와 현재 CombatData/Session의 가격·증가량 경로를 읽은 뒤, `--through 3 --out docs/development/skill_rules_validation_20261013/balance_example`로 실제 실행했다. 최신 플레이어 성장 노션도 직접 fetch했다.

- **확인 데이터(구현/기획):** stage 플레이어 피해10·공속1, upgrade 피해Delta2. 실제 가격은 CSV의 costIncrement만 읽으면 안 되며 Session→CombatData.PlayerUpgradePrice 경로를 따른다. 최신 노션의1/2/3강화100/140/190과 일치한다.
- **추정(정적 계산):** 전원 처치·무지출 기준 누적 골드45→93→143, 첫100골드 강화는3R까지 확보 가능. 무방어 공격형HP25는 피해10→12에도3발로 동일, 발사 간격 구간2초도 동일. 지속 명중 가정 화력10→12는 실전DPS가 아니다. 사거리·비행·다른 공격자·코어 도착은 미계산.
- **주관적 평가/원인 가설:** 첫 강화 전 선택 공백이 지루할 가능성은 사람 플레이 미검증이다. ‘공격력+20%=클리어20%단축’이라고 해석하지 않았다.
- **제안 비교:** 첫 강화 시점/비용 조정은 선택을 앞당기지만 성장 경제를 바꿈; 공격형HP 경계 조정은 발수 차이를 드러내지만 난이도를 바꿈; 전후 스펙/명중 피드백은 규칙을 유지하지만 실제 처치시간 차이를 만들지는 않음. 현 근거로는 HUD 피드백 개선을 먼저 연결하고 수치 변경은 사람 플레이의 공백/선택 체감 측정 후 검토한다.
- **검증:** 실제 1배속 첫 구매 시각·무행동 구간·강화 전후 처치 발수/동일 조건 시간과 선택 이유를 기록해야 한다. 보스/증강/전체1~11 분석은 이번 좁은 예시에 포함하지 않았다.

출력: [rounds.json](balance_example/rounds.json), [growth.json](balance_example/growth.json), [정적 밀도 그래프](balance_example/pressure.svg). 종료코드0, missing_rounds=[].

## 예시 2 — HUD

요청: `$core-guardian-hud-ux 현재 플레이어 강화 패널에서 성장량을 확인할 수 있는지 분석하고, 전투 시야를 유지할 배치안 3개를 제안해 줘.`

최신 HUD 노션 직접 fetch와 현재 CoreGuardianHud.Build/Refresh, Session 구매 경로를 읽었다. 기존 실행 Canvas 스냅샷·Game View·7항목 시험 보고서를 재사용했으며 새 세션/회귀/계측기를 만들지 않았다.

- **구조/확인 데이터:** 런타임 uGUI, 플레이어 오른쪽 아래 패널. 현재 네 버튼은 이름·가격뿐이고 타워 상세는 현재값·가격이다. 강화 현재→다음·증가량은 미표시.
- **추정:** 증가량을 구매 위치와 연결하면 인지 부담이 줄어들 수 있다. 과거 사진의 경로 겹침은 화면 사실이며 실제 적 놓침은 별도 가설이다.
- **주관적 UX 평가:** 성장 만족감이 부족할 가능성, 상시 숫자가 산만할 가능성은 사람 검증 전 평가로 표시한다.
- **우선순위:** 코어/단계/재화 상시, 구매 비교 상세, 성공 직후 증가량 사건 표시. 상세 DPS는 조건을 붙이고 통합 전투력 공식은 만들지 않는다.
- **3안/장단점:** A 기존 패널 비교+짧은 피드백(익숙한 조작, 펼친 타워 가림 잔존), B 하단 좌우 상세(진입 시야 확보, 하단 혼잡), C 작은 상시 요약(성장 재확인, 상시 정보 증가). A추천, 구매 대상/증가량 판독·연속 구매/실패·이동 시야·다른 화면 비율을 직접 플레이테스트한다.

상세7항목/와이어프레임은 [HUD 시험 보고서](../hud_ux_analysis_20261013/report.md). 이전 독립 사용 시험: [HUD 검증](../hud_ux_analysis_20261013/validation.md), [밸런스 검증](../balance_analysis_20261013/validation.md).

## 설치/형식 검증

프로젝트의 두 `SKILL.md`와 개인 설치본의 내용 동일성을 확인한다. 프로젝트/설치 각각 `quick_validate.py` 통과를 확인한다. 검증은 스킬 구조·예시 행동 범위이며 게임/밸런스/UX 승인으로 처리하지 않는다. 과거 분석보고서의 당시1~9R 구현 범위는 역사적 스냅샷이며, 현재1~11R 상태를 그 보고서로 대체하지 않는다.
