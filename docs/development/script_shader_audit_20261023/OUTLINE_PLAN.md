# 윤곽 중복 조회 축소 계획안

2026-10-23 작성 후 사용자 “진행해”로 실행 승인. **실행 결과: 후보 검증 후 일반 프레임 비교 악화로 제품 원본 복구·후보 격리 보류.** [실제 결과/원본/한계](../outline_sampling_20261023/README.md). 아래는 승인받은 계획이며 완료를 성능 개선 통과로 해석하지 않는다.

## 목표와 추천 방식

화면 결과와 두께를 유지하면서 동일 mask의 중앙 중복 읽기와 판정 이후 남는 이웃 조회를 줄인다. 제품 변경은 SelectionOutline.shader의 fragment 경로1곳으로 한정한다. C# 마스크 생산·RT·정렬·원본 출력·보류 배칭·아틀라스를 바꾸지 않는다.

|선택지|장점|한계|제안|
|---|---|---|---|
|중앙값 재사용만|작은 변경, 제어 흐름 변화가 적음|폭1의 코드상 최대10→9회. 컴파일러가 이미 중복 제거했다면 이득 없을 수 있음|1단계 기준 후보|
|중앙 재사용 + edge 확정 시 종료|가까운 이웃에서 경계를 찾는 픽셀의 나머지 조회 생략 가능|GPU wave 분기·샘플 파생값 문제를 다뤄야 하며 악화 가능|**권장. 단계별 비교 후 좋은 쪽만 채택**|
|폭1/2 전용 고정 이웃 나열|동적 loop 비용을 줄일 가능성|분기를 잃거나 명령 수가 늘 수 있고 variant/검증 범위 증가|첫 작업에서 제외. 앞선 두 후보 근거 후 별도 결정|

## 구체 변경

1. 중앙 mask는 현재와 같은 정밀도의 값으로 한 번 읽어 보관한다. 첫 `clip(.5-center)`는 순서와 비교 기준을 유지한다.
2. 기존 `half edge` 누적과 같은 변환 규칙으로 중앙값을 반영하고, 이웃 순회에서는 (x=0,y=0)을 다시 읽지 않는다. **단순히 중앙을 제외하고 edge=0으로 두지 않는다.** 중앙 .5와 half 경계 부근은 원본 판정이 달라질 수 있다.
3. 누적 edge가 `.5 이상`이면 최종 출력색이 이미 결정됐으므로 `_Color`를 반환한다. 끝까지 못 찾으면 원본처럼 discard한다. 원본 y/x 순서의 나머지 이웃은 유지한다.
4. 이웃마다 서로 다른 픽셀이 일찍 종료하는 구조에서는 implicit LOD의 화면 파생값에 의존하지 않도록 해야 한다. 현재 입력이 Point/Clamp, mip 없는 body RT인 계약을 먼저 확인하고, 조기 종료 후보의 이웃 읽기는 명시적 LOD0를 사용한다. 계약을 확인할 수 없으면 이 후보를 적용하지 않는다. 이를 단순 정밀도 변경과 섞지 않는다.
5. `_Width`0~8의 일반 경로를 유지한다. `_Color`·Blend·Pass·ZWrite·마스크 alpha threshold·UV/클램프·출력 정렬은 바꾸지 않는다. BatchedMaskOutput/AttackBodyBatch/접촉/발광은 수정하지 않는다.

최대 코드상 조회는 폭1에서10→9, 폭2에서26→25이며 조기 종료의 최소 횟수는 실제 mask/판정에 따라 달라진다. 코드를 줄인 비율을 GPU/FPS 개선율로 환산하지 않는다. 중앙값의 `.5` 판정은 first clip과 half 누적을 분리해 보존한다.

## 파일과 실행 순서

- 제품 대상: `Assets/Art/Rendering/Shaders/Resources/CoreGuardian/SelectionOutline.shader`.
- 대상 검증: `Assets/Scripts/Tests/EditMode/CoreGuardianSelectionOutlineTests.cs`의 기존 실제 렌더 검사와 작은 원본/후보 이미지 대조를 사용한다. 검증이 필요하면 `CoreGuardianSelectionOutlineShaderTests.cs`를 같은 EditMode 폴더에 추가한다.
- 원본 비교 shader는 테스트 전용 고유 이름 `Hidden/CoreGuardianTests/SelectionOutlineReference`로 별도 fixture에 보관한다. 제품 shader와 이름/Resources key가 충돌하지 않게 한다. 원본 소스·hash는 실험 폴더에 보존한다.
- [ ] 승인 후 실제 HEAD/diff·현재 shader hash, Unity 연결/씬/dirty/Play/컴파일/다른 검사부터 확인한다. 사용자 작업은 건드리지 않는다.
- [ ] 동일 카메라/입력/재질에서 원본 출력과 후보를 실제 렌더해 비교하는 기준을 먼저 고정한다. shader 문자열 검색이나 CPU 알고리즘 복사 테스트만으로 완료하지 않는다.
- [ ] 중앙 재사용만 적용한 후보의 픽셀 동등성을 확인한다.
- [ ] 조기 종료+명시 LOD0 후보를 따로 적용하고 원본 및 앞선 후보와 비교한다. 각 단계 source/hash와 결과를 분리한다.
- [ ] 최종 후보만 기존 적128/타워15·1920×1080/ortho8.5·동일 dt·원본 출력 조건에서 원본과 일반 모드 warm15/sample90 각1회 예비 비교한다. Deep/할당스택/Frame Debugger는 켜지 않는다. 단회는 기존 작업의 제한된 길이를 따른 예비값이며 확정 성능 통과가 아니다. 추가 반복은 자동 실행하지 않는다.
- [ ] 종료/자체 상태 복원을 실제 확인하고 수치·원본·악화·미검증·판정을 기록한다. 제품 원복은 이번 shader 수정만 대상으로 한다. 전체 Git restore/reset은 금지한다.

## 성능 판정과 중단 기준

- 전체 frame ms·최소/최대/평균 FPS·Draw/SetPass·GC 및 유효한 GPU ms를 기록한다. 이 변경은 GPU 후보이며 C# 마스크 CPU4.672ms를 직접 없애는 작업이 아니다. draw 수 감소도 목표로 잡지 않는다.
- 기존 D3D12 GPU Profiler 지원 한계 때문에 실제 GPU ms를 얻을 수 있는지 승인된 실행 준비에서 확인한다. 얻지 못하면 **GPU 절감 미검증**으로 남긴다. 그래픽 API 변경·새 도구 설치·빌드/실행파일 실행을 자동 대안으로 쓰지 않는다.
- 픽셀 차이1개라도 생기면 해당 후보 채택을 멈추고 원인을 보고한다. 조기 종료가 느려지면 그것만 제외하고 중앙 재사용 후보와 원본을 비교한다. 차이가 변동 범위 안이면 성능 개선 확정/자동 채택으로 표시하지 않는다.
- 컴파일/측정 timeout·예상 밖 부하·사용자 Play/검사 충돌이면 재시도/대체검사 없이 중단·현재 상태/복구 방법을 보고하고 새 허락을 받는다.

구현+대상 검증 예상15~25분. 실제 실행은 이 계획에 대한 별도 승인 후 시작한다. 현 시점에는 계획 문서만 작성했으며 Unity/제품 코드/씬/설정/커밋/push는 변경하지 않았다.
